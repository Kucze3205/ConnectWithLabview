# Setup decisions

The accepted outcome of the setup map ([#1](https://github.com/Kucze3205/ConnectWithLabview/issues/1)). It replaces `setup-notes.md`, which the arming ticket ([#8](https://github.com/Kucze3205/ConnectWithLabview/issues/8)) deleted. Owner decisions are kept here together with the specific guarantees they lose and what replaces each one. A lost guarantee informs the owner's choice; it is not a veto. Evidence and details stay in the linked files. After arming, only the owner changes these decisions (`docs/perpetua/engine.md`, "Authority after arming").

## Lost guarantees and their replacements

| # | Guarantee lost | Replacement and where it is implemented | What stays unverified |
|---|---|---|---|
| 1 | The shipped Claude-only credential probe and subscription-limit parking | Routed Claude/Codex/Copilot execution: `provider_pool.py`, `provider_adapter.py`, `provider_rpc.py`, `cloud_probe.py`, `role_runtime.py`, `runtime_checkpoint.py`. Probes separate authentication, entitlement, quota, throttling and service failure; limits park the session, fall back along `policy/params.yml` `routing` and resume from the continuation the epilogue publishes to `loop-runtime`. | A successful structured Claude task (Claude reported subscription exhaustion in every cloud run). Owner-deferred; runtime availability probes and fallback remain mandatory. `claude-haiku-5-5` has no catalog or inference check. |
| 2 | OpenAI's recommendation to run account-auth CI only in private repositories | Owner-controlled workflow refs, no credentialed PR jobs, `provider-*` environments restricted to `main` and `perpetua/setup`, one serialized refresh stream (`credential_store.py`, `credential-maintenance.yml`, concurrency group `provider-credential-codex`), a scoped GitHub App with Environments write, and storage-write authority kept away from models and tools. | The topology is not officially recommended. An interrupted credential rotation cannot be recovered unattended; it needs a new dedicated login. Claude's one-year setup-token (set 18 Oct 2026) needs replacing before it expires; reissue is not unattended. |
| 3 | The in-runner isolation of 0.5.0 (bubblewrap mount/PID/network namespaces around model CLIs and broker commands, seccomp socket denial for offline roles, the immutable executor snapshot). Removed with engine 0.6.0 (owner decision 1 Nov 2026); #24 tested this boundary and is obsolete. | The 0.6.0 machine boundary: the session job has no GitHub permission and only the model credentials; the epilogue (a fresh runner) admits files as data with write/protected-path checks. | A model or command in a session can read that session's model credentials and reach the network; the response to a leak is revoking them. Offline roles are no longer offline. |
| 4 | The automatic quality gate | `gate.kind: owner` with `gate.owner_paths` (owner decision 6 Nov 2026, after 13 routine merge requests all accepted): only work touching the verification method (`benchmark/protocol.md`), the baseline design (`benchmark/baseline/`), resource proposals (`benchmark/resources-proposal.md`) or `docs/perpetua/` waits for the owner; other work merges once `check` passes. A policy/ rollback notifies the owner only from the second in a row (`rollback_notice_after: 2`); `check` (`policy/evaluator/evaluate.py --check`) verifies evidence integrity only and states that quality is unmeasured. Policy and evaluator changes go through the independent verifier (`policy/roles/evaluator-verifier/`). | Tool quality; there is no benchmark and no accepted threshold. |
| 5 | A goal gate | None. Without an accepted `goal/gate.yml` (`owner_confirms: true`) the loop never declares its own end. | Whether the goal is reached. |
| 6 | Running LabVIEW from roles; isolation of withheld evaluation cases | Native LabVIEW work runs only in separate trusted cloud jobs (NI 2026 Q1 headless container, digest-pinned, `labview-runtime.yml`); roles get no Docker access and stay offline. | Roles cannot execute LabVIEW directly. This public repository gives no secrecy to withheld cases; a restricted store needs a concrete owner grant. Native LabVIEW 2024 execution and all-version compatibility are unverified. |
| 7 | Immediate recovery from provider exhaustion | Bounded backoff (`provider_pool.backoff`), shared availability state (published by each epilogue, newest observation wins); the watchdog's 24 h rule and repeated-failure outages still apply. | If every provider is limited, work parks; no spending is authorised to avoid that. |
| 8 | A per-turn push of source to `task/N` and per-turn upload of role outputs to release `loop-checkpoints` during a routed session. Since 0.6.0 the session job has no token: checkpoints are local commits; source and outputs reach `task/N` only when the epilogue admits the results artifact. | The continuation (`sessions/N.json`) and availability are published by the epilogue; The live proof of the 0.6.0 layout is the manually dispatched `routed-proof.yml` (all three providers produced accepted turns on 1 Nov 2026, see ticket M9); the setup-era remote-checkpoint proofs (`runtime-proof`, `runtime-resume`) were removed. | Source written by a session whose runner is killed before its results artifact uploads is lost; the issue parks and the next session restarts from the last admitted files. |
| 9 | A trial run before arming | None by design: iteration 0 is the trial. The setup was exercised through the roles runtime runs listed in [cloud-authentication.md](cloud-authentication.md), without merging to the default branch. | The deployed workflows have not run on the default branch. |
| 10 | Copilot authenticated with the workflow's `github.token` (`copilot-requests: write`). | The `COPILOT_REQUESTS_TOKEN` secret in environment `provider-claude`: a token limited to Copilot requests, created by the owner. | Until the owner creates it, Copilot candidates fail authentication and routing falls back to Claude and Codex. |

## Stays unchanged

The shipped GitHub issue owner-request channel (acceptance, refusal, frozen payloads, close-event wake-ups), the protected zones in `engine.yml` and the Policymaker's permissions are unchanged. Only the owner changes the engine, accepted limits, the goal gate and `AUTOPILOT`.

## Arming

Performed by [#8](https://github.com/Kucze3205/ConnectWithLabview/issues/8): merge `perpetua/setup` into `main`, tag the merge commit `setup-baseline`, run `python3 .github/loop/setup_roles.py validate --baseline setup-baseline` from a clean checkout of that commit, then set `AUTOPILOT=on` and run `watchdog.yml`. The result and links are in the ticket's comments.

## Baseline tag

`setup-baseline` was moved by the owner on 23 Oct 2026 from `8fa87b7` to `7e83c72` (engine update 0.3.0 → 0.5.0, which changed `engine.yml` and `policy/prompts/policymaker.md`). Since engine 0.5.0, `validate --baseline` compares the managed-definition revision, not the commit SHA, so engine-only fixes under `.github/loop/` do not require moving the tag. Move it again only after an owner-approved change to the managed definitions (`/perpetua:update`); the watchdog uses it to roll back `execution/` and `policy/`. Validation also counts ignored files in `execution/` and `policy/`: remove any `__pycache__` there or run tests with `python -B`.
