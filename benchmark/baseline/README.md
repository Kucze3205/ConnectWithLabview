# Baseline comparison design

This is an unreviewed design artifact for the [protocol baseline](../protocol.md#baseline) and [evaluation contract](../../docs/perpetua/evaluation.md). No paired comparison or development pilot has run. It establishes no benchmark readiness, quality threshold, spending grant or accepted precision target. [Accepted limits](../../docs/perpetua/accepted-limits.md) govern resource use and data routing.

## Manifest contract

[run-manifest.template.json](run-manifest.template.json) inventories the configuration and evidence that must be frozen before comparison. Each undecided field has `value: null` and an explicit `reason`; the schema version is structural metadata. No provider, recipient, model, quota, repetition count or budget is selected. Restricted cases, keys, revealing hashes and run records belong in the approved restricted boundary, never in this public template or repository history.

The fields cover model identity and modalities; prompts and all shared inputs; minimal arm instructions; reader, tool, runner and scorer versions; split, keys and native evidence; matched budgets; repetitions, order and stopping; isolation and preservation; fixed scoring inventories; separate fidelity probes; coverage; uncertainty; and time, token and cost accounting. A later concrete run manifest must supply actual values and resolvable evidence after review. It must preserve full prompts, schema and input identities, rather than merely naming mutable resources.

Run `python3 -I benchmark/scripts/baseline.py --check` from the repository root. The stdlib-only checker reads only the adjacent template and uses no environment variables, network, native runtime or prepared sources. Its frozen required-field list rejects missing or extra fields, non-null undecided values, missing reasons, duplicate JSON keys and nonstandard constants. This validates the undecided template structure only; it neither validates a populated run manifest nor establishes substantive correctness or review approval. A populated manifest requires a separately reviewed validation contract; do not relax this template check to imply execution readiness.

## Development-pilot-only precision/cost method

1. Resolve the blockers before dependent measurement: accepted cases/keys/split, tested isolation, verified model quota and an independently reviewed executable scorer. Development pilots use independently checked development cases only. No withheld case, key, answer, comparative result or revealing evaluation feedback may guide pilot selection or tuning. Verify permitted recipients and retention before routing any material.
2. Design paired development sessions with the same question, original artifacts, documentation, available native images and presentation order. Supply text artifacts directly to both arms. Only reader access and its minimal instruction differ. Verify model image support and record unavailable modalities. Match total token, context, output and wall-time budgets, including reader responses in context; declare tool-call limits and exhaustion/truncation outcomes.
3. Exercise fresh isolated sessions, randomized paired arm order and preservation of raw requests, responses, model identifiers, usage, errors and timestamps. Check that the scorer retains omissions, extras, duplicates and contradictions under frozen inventories and separate correctness/grounding rules. Execute required fidelity probes in separate recorded reader sessions with independent native references; no-tool fidelity is not applicable and supplies no paired fidelity estimate.
4. Estimate resource use from development pilots: end-to-end and tool time, input/output tokens, reader calls, retries, cache effects and queue time. Measure probe time/cost separately. Distinguish provider-reported costs from estimates; pin the dated price schedule, billing units and assumptions. Identify infrastructure and unpriced resources explicitly; unknown costs remain unknown. Use existing resources within verified limits; additional spending requires a concrete owner grant.
5. Examine development paired-difference variability separately for correctness and grounding and by the declared coverage strata. Resample independent project/lineage groups, retaining all related cases and repetitions within each sampled group. Use these pilots to assess candidate repetition and allocation plans against available quota and an owner-accepted precision target. More repetitions do not create additional independent projects; report small-sample limits and missing coverage. No numeric repetition count, threshold or spending is assigned here.
6. Before evaluation results exist, document and freeze the chosen independent repetitions per case/arm, sampling order, arm randomization and seed, stopping rule and affordable run ceiling. Freeze the uncertainty procedure, confidence level, resampling seed/count, lineage units, treatment of missing pairs, per-case tolerances/nondeterminism, exclusions and any within-dimension weights. Preserve the pilot evidence and rationale under a revision identified by `precision_cost_plan_revision`. Any acceptable uncertainty target or quality threshold needs owner acceptance.
7. Freeze the complete run manifest and obtain independent method review. Evaluation must reuse matched case/key revisions and scoring rules without prompt tuning or favorable-repeat selection. Missing repetitions, quota exhaustion or incomplete pairs prevent a completed comparison; retain their records and coverage counts. Report planned, attempted, executed, scored and complete-pair counts, required-item and extra-claim outcomes, incomplete probe scope, separate dimensions and uncertainty, and separate answer/probe resource accounts. Predeclare how operational interruptions are handled without using observed arm advantage.
